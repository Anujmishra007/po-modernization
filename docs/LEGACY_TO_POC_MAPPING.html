Deep Dive: Dynamic Hooks (String SP names) vs Java Plugins

The Problem: What are Dynamic Hooks?

In the legacy system, when a PO is populated into an ASN/Receipt, the system needs to run client-specific customizations. But instead of hardcoding which client uses which logic, it stores SP names as strings in a config table, then executes them dynamically using sp_executesql.

Legacy Dynamic Hook Resolution Flow

│  LEGACY: Dynamic Hook Resolution                                            │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  1. User calls: lsp_ASN_PopulatePOs_Wrapper('PO-001', 'NIKE', 'KR01')      │
│                              │                                              │
│                              ▼                                              │
│  2. Wrapper calls: isp_PrePopulatePO_Wrapper                               │
│                              │                                              │
│                              ▼                                              │
│  3. Read config:  SELECT PrePopulatePOSP                                   │
│                   FROM STORERCONFIG                                         │
│                   WHERE StorerKey = 'NIKE'                                  │
│                              │                                              │
│                              ▼                                              │
│  4. Result:       @spName = 'ispPRPPLPO_NIKEKR'  ← STRING value!           │
│                              │                                              │
│                              ▼                                              │
│  5. Dynamic exec: EXEC sp_executesql @spName, @params  ← Executes string!  │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

Legacy SQL Code (Simplified)

-- isp_PrePopulatePO_Wrapper (148 lines)
CREATE PROCEDURE isp_PrePopulatePO_Wrapper
    @c_ReceiptKey NVARCHAR(10),
    @c_POKeys NVARCHAR(MAX),
    @c_StorerKey NVARCHAR(15)
AS
BEGIN
    DECLARE @spName NVARCHAR(100)

    -- Step 1: Read SP name as STRING from config table
    SELECT @spName = PrePopulatePOSP
    FROM STORERCONFIG
    WHERE StorerKey = @c_StorerKey

    -- Step 2: If config has a value, execute it DYNAMICALLY
    IF @spName IS NOT NULL AND @spName <> ''
    BEGIN
        -- Build dynamic SQL with string SP name
        DECLARE @sql NVARCHAR(MAX) = @spName + ' @ReceiptKey, @POKeys, @StorerKey'

        -- ⚠️ Execute the string as code! DANGEROUS!
        EXEC sp_executesql @sql,
            N'@ReceiptKey NVARCHAR(10), @POKeys NVARCHAR(MAX), @StorerKey NVARCHAR(15)',
            @ReceiptKey = @c_ReceiptKey,
            @POKeys = @c_POKeys,
            @StorerKey = @c_StorerKey
    END
END

Problems with Dynamic Hooks

No compile-time validation

SP name typo = runtime crash

No dependency tracking

IDE can't find "who calls what"

SQL injection risk

String execution = security hole

Hard to test

Can't mock the dynamic SP

Version control nightmare

SP logic lives in database, not Git

No type safety

Wrong parameters = silent failure

POC Java Code Example

// VariationResolver.java - Resolves which plugins to use
@Component
public class VariationResolver {

    private final List<PrePopulatePlugin> prePlugins;
    private final ClientConfigRepository configRepo;  // PostgreSQL

    public List<PrePopulatePlugin> resolvePlugins(String client, String region) {
        // Read CONFIG DATA from PostgreSQL (not SP names!)
        ClientConfig config = configRepo.findByClientAndRegion(client, region);

        // Return Java plugins that match this client
        return prePlugins.stream()
            .filter(p -> p.supports(config))  // ✅ Compile-time safe!
            .collect(toList());
    }
}

// NikeKoreaPrePopulatePlugin.java
@Component
public class NikeKoreaPrePopulatePlugin implements PrePopulatePlugin {

    @Override
    public boolean supports(ClientConfig config) {
        return "NIKE".equals(config.getClient())
            && "KR".equals(config.getRegion());
    }

    @Override
    public void execute(PopulateContext ctx) {
        // This replaces ispPRPPLPO_NIKEKR stored procedure
        // But it's:
        // ✅ Compile-time validated
        // ✅ Unit testable
        // ✅ Type safe
        // ✅ Version controlled in Git
        // ✅ IDE can find all usages

        if (ctx.getHeader().getMissingCustomsCode()) {
            ctx.addValidationError("Customs code required for Korea");
        }
    }
}

KEY INSIGHT: PostgreSQL/SQL Server in POC stores DATA (config flags,
feature toggles), not CODE (SP names to execute). The business logic
lives in version-controlled, compile-time safe Java plugins.
